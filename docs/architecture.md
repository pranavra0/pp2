# Runtime design

## Evaluation and authority

A peer accepts one operation per mutually authenticated TLS 1.3 connection. It looks up the capability by both its random ID and the caller's authenticated identity. The peer controls the reference the capability addresses. A grant allows snapshot reads or snapshot reads and atomic updates. Indexed references grant reads or reads and transactional row updates. A grant can restrict either kind of reference to one immutable program hash. A grant holder may delegate an equal or narrower grant to a different identity, with a maximum depth of eight. Revoking a grant removes its descendants and their receipts in the same transaction.

A snapshot read runs against one immutable state block. The peer rechecks authorization before releasing a result. A snapshot update uses an expected revision and returns exactly {next, value}. The peer checks the revision and grants inside the committing transaction, then saves the next content block, the reference advance, and a receipt together. Reads see the revision they started with. Authoritative updates have a total order at the owning peer. [Replicated resources](#replicated-resources) can also declare a multi-writer history.

Use the same grant, program, input, expected revision, and operation ID when retrying an ambiguous update. A recent match replays the receipt. Reusing an ID with different arguments while its receipt is retained produces an error. Receipts are retained for 1,024 revisions while the grant remains live. When the revision has advanced past that window, a conflict can establish that the retry did not apply now. The client must reconcile older outcomes through application state. The `peer delegate` command creates a distinct grant on each success. The graph attenuation operation described below replays the same live grant for an identical request.

The caller chooses the entry peer. The client reports elapsed time and application bytes in both directions, including code negotiation. Rust callers can use `Cancellation` to close a synchronous evaluation. Its worker stops when the request connection closes or the daemon exits. Cancellation can race a commit, so recovery uses the same update receipt mechanism.

## Peer identity and discovery

In stable identity mode, a peer ID is a domain-separated SHA-256 hash of an Ed25519 public key. Peers sign role-specific TLS 1.3 exporters to prove possession of the corresponding private key on the current connection. The client verifies the expected destination ID before presenting its own proof or sending any grant, program or input. The server checks its local identity policy before accepting a pp2 request. Independently administered nodes can use their own transport certificates, including self-signed certificates. The certificate authenticates the TLS handshake key and the exporter proof establishes the pp2 identity. Certificate mode continues to use CA validation, TLS names and certificate fingerprints.

Address changes and transport certificate replacement retain the same identity when the operator keeps the identity key. Replace a lost or compromised identity key by provisioning a new ID and reissuing grants and bindings for that ID. Jobs and subscriptions remain bound to the identity that submitted or installed them. Resume work under a replacement identity by explicitly resubmitting or reinstalling it under new grants. To deny a compromised identity at a node, add its ID to `revoked` in that node's discovery configuration and restart the daemon. It then rejects inbound and outbound sessions for that identity and queued jobs submitted by it. Each resource owner can revoke the affected grants to remove their delegated descendants. Revocation policy is local to each operator.

Listening peers sign short-lived location leases. IPv4 LAN advertisements use multicast group `239.255.73.42:47342` with a one-hop limit. The listener periodically refreshes its selected interface, including after an address change. A received lease supplies a LAN route when its signed LAN address matches the datagram source. Every route still requires the TLS identity proof. A lease expires eight seconds after issuance and the receiver accepts issuance at most two seconds ahead of its clock. The newest valid lease supersedes older leases. Conflicting locations with the same issuance time quarantine the identity's discovery routes until a newer valid lease arrives or the leases expire. Explicitly pinned routes can still authenticate the identity during a discovery conflict. Operators run one active endpoint advertiser per identity and keep clocks synchronized.

A node can publish the same leases to a configured rendezvous service. It can also offer up to two outbound sockets for the relay to pair with incoming connection attempts for its ID. A fresh, signed challenge proves possession of the receiving identity before a socket can be offered. A paired socket carries the same end-to-end TLS handshake and operation as a direct connection. The service can observe connection metadata, withhold leases or drop traffic. Destination authorization, the operation state and the encrypted payload stay with the peers. Each node tries live LAN routes, configured pins and signed direct addresses before relaying. Once a route is authenticated and a request sent, the transport leaves ambiguous operations to the existing receipt or job retry mechanism.

The directory retains up to 64 identities and each lease can advertise four direct addresses plus its LAN route. Rendezvous caps simultaneous control requests at 32 and, when enabled, relayed sessions at 32. Each tunnel has a 12-second lifetime and an 8 MiB allowance per direction. Discovery work fits inside the caller's deadline and uses bounded route attempts and frames. A synchronous invocation can report `peer-unavailable` when it cannot establish an authenticated route or `timeout` when its deadline runs out. Durable effects retry temporary unavailability until their deadline. Locally available work and configured direct paths can run while rendezvous is offline. [TLS 1.3 exporters](https://www.rfc-editor.org/rfc/rfc8446#section-7.5)

## Guest effects and placement

A graph starts at an explicitly selected peer against one indexed reference and one program. Its input includes a deadline, a call count, a maximum depth, and named capabilities. The executing peer resolves named local bindings against the authenticated caller identity, entry grant, and entry program. An authenticated peer can also attach recipient-bound grants. Attachments contain an issuer identity, opaque grant ID, pinned program, and access. The host resolves that identity to a route and authenticates the destination before sending a grant.

The worker sees opaque JavaScript objects with invocation-local identity. It can pass an explicit subset to `pp2.evaluate`. JSON values convey no authority. For each selected capability, the current executor asks the issuing peer to narrow it to the child identity, program, permitted access, graph limits, and expiry. The child holds those capabilities and authenticates to the next destination as itself. The destination checks the authenticated holder, the presenting peer associated with the attachment, the program and operation, the active grant lineage, and all grant ceilings. Issuers deny authority expansion and remove descendant grants on revocation. The guest sees only the resulting invocation-local objects.

Each call consumes one graph call plus the descendant allowance assigned to it. Every executor applies the remaining depth and budget to its own outgoing effects. The hard ceilings are 16 remote calls, four remote levels, 16 bindings per invocation, and eight seconds per attempt. A branch may shorten the inherited deadline. Each worker can submit up to 128 effects, and failed calls consume their reservations. Metrics aggregate remote attempts, frames, and results reported by participating peers.

Synchronous calls remain tied to their immediate connection. Closing the entry connection stops its worker and closes its outstanding child connection, which propagates cancellation down the active branch. Guest promises enqueue effects in order. Returning with unsettled effects fails the invocation.

An update is a leaf. It names an expected collection revision and operation ID. Commits and receipts belong to the destination, and a failure later in the graph leaves an earlier committed update in place. Independent peers can observe different revisions. The update receipt rules apply to synchronous retry.

## Durable computations

A durable job uses the graph evaluator and the same worker isolation. Its identity is the submitting peer identity and a client-chosen job ID at the selected peer. Acceptance commits the immutable program and input hashes, the verified code and input blocks, the resolved capabilities, the graph budget, and the absolute expiration. Binary database timestamps use Unix milliseconds. Peers need reasonably synchronized clocks for deadlines. An identical submission retrieves the stored status. Changing an argument under an existing identity fails.

The peer owns the job after acceptance. It runs up to four durable attempts concurrently, with at most 32 active jobs per submitter and 64 per peer. A new job may live up to five minutes. The attempt deadline and worker limits apply each time it runs. One daemon serves the database at a time. After a process restart it requeues interrupted attempts from SQLite. Garbage collection retains the verified input and program graph while a job is active. Terminal job IDs, program and input hashes, and results are retained in the database and share its page quota.

A durable remote effect first records its intent and a stable child ID, then submits a durable child directly to its destination. Pending children and temporary transport failures cause the parent to yield its worker and retry. The parent journals terminal child outcomes. Re-evaluation can reuse those outcomes or retrieve them from the child if acknowledgment was lost. Changing or skipping a previously recorded remote effect fails recovery. Local reads are snapshot-consistent within each attempt and can observe a new revision on replay.

A durable local update commits collection changes, revision, retry receipt, and job completion in one SQLite transaction. A crash before that transaction commits rolls it back. Workers and messages can repeat, and child effects use durable identities to recover their committed outcomes. Transactions cover an individual peer and collection.

The submitting identity can query or cancel its jobs on a new connection. A committed cancellation stops local execution and prevents local completion. If completion won the race, cancellation returns the completed state. Expiration prevents new work and commits under that job's execution deadline. Children already accepted at other peers can finish within their own bounds, and committed effects remain in place. An entry grant revoked before completion denies further work under that grant. Terminal outcomes for ordinary references belong to the submitting identity and remain retrievable after grant revocation. Jobs against replicated resources require current authority to retrieve their results and include the resource view in successful completions.

## Persistent applications

A local administrator installs a named application for the daemon's authenticated identity. The database retains each subscription's immutable JavaScript program, local watch and entry grants, named remote grants, graph budget, expiration, and delivery cursor. Installation validates the full handler module graph and pins it for garbage collection while the subscription is active. The watch and entry grants must each be read-only, bound to the daemon's identity, and pinned to the handler. The watch grant identifies one reference. The handler reads from the indexed collection selected by the entry grant, which defaults to the watch grant. Remote capabilities come from the installation and remain subject to the issuer's identity, program, access, delegation, and expiry checks.

Each reference creation and successful revision advance commits an event with a stable random ID in the same transaction as its state changes. An operation receipt replay returns the original result without a second revision or event. A subscription starts at the current revision on installation. Events carry the reference name and revision. They carry no snapshot or row values. Handler reads see the collection snapshot for the current attempt. An application that needs the values from a specific revision can store them under an immutable revision key in the same transaction as the resource update, as the inventory example does.

The daemon enqueues at most one delivery per subscription at a time, in revision order. Acceptance durably associates the event and subscription with a deterministic job ID and journals remote effects through the existing durable job mechanism. On completion, the daemon retires the revision and stores its terminal outcome atomically. Temporary transport or storage failures retry within the job's deadline. Handler failures, authorization failures, and expired deliveries retire the revision and let the next event proceed. Worker attempts may repeat, and a child may commit before a later effect fails. Use stable operation IDs and idempotent application updates where retries matter.

Each application can install up to 16 subscriptions and a peer can have up to 128 active subscriptions. Deliveries share the four durable workers and the existing active job limits. A full queue leaves events on the log, and a full destination queue returns a retryable busy response for reaction jobs. Each delivery lives for up to five minutes or until its subscription expires, whichever comes first. The event log keeps up to 4,096 events per peer. The serving daemon also prunes events older than 24 hours. A cursor that falls behind reports missing revisions and resumes at the next retained revision. Once enqueued, a delivery retains its event input independently of the log. Each subscription keeps its latest terminal outcome. Remote reaction results remain available until five minutes after their deadline so a retrying parent can recover them.

Reactions run in the same bounded worker and graph as explicit durable jobs. The host propagates reaction origin to descendants. A destination must issue a pinned reaction-writer grant for a reaction to update its collection. Ordinary updates require ordinary grants. Reaction writes create events, and subscription cursors skip those events at every peer. This bounds execution to one generation of subscriptions per ordinary state transition while allowing the reaction's explicitly budgeted graph to use multiple peers.

The watched resource owner or entry resource owner can revoke the relevant grant, which cancels local deliveries and disables the subscription. The installer can also revoke a subscription directly. Removing an installation revokes its local subscriptions and cancels their pending and running jobs in one transaction. Before dispatching a child, the daemon records its absolute deadline. The application reports `removing` until those deadlines pass, and `removed` afterward. A child accepted by another owner may finish before its deadline or be cut off by that owner's revocation. Committed updates persist. Installation records and names are retained after removal. Resuming an installation requires the original serving identity.

## Host resources

A host resource is an indexed reference with an immutable provider name and private configuration. The administrator registers a provider with `Server::with_host_provider` and creates a scoped resource with `PeerStore::create_host_resource` or `share_host_resource`. The latter issues a program-pinned grant in the same transaction. Existing grant rules select the reference, holder, program, access, and delegation lineage. The collection stores data such as an index. Its writer grants permit collection updates.

When the active collection has a resource, the worker receives an opaque `pp2.resource` handle. Calling `pp2.call(handle, operation, input)` sends a bounded request through the existing worker effect channel. The runtime holds the provider configuration and gives the worker a bounded data result. Providers validate requests and enforce their own resource scope. A named graph binding to a resource's pinned program runs beside the resource and uses the same guest API as a local invocation. Resource reads can repeat after a durable retry. Providers supply read operations so their use preserves collection update and replay semantics.

For read invocations the peer checks current authority before and after a host effect, at provider checkpoints, and before publishing the invocation result. For updates, the collection transaction serializes against revocation. A committed revocation prevents further work under that grant. An update that commits first follows the normal receipt rules.

The Linux directory provider opens the selected root without following symlinks and records its device, inode, and creation timestamp. It checks that identity on each operation. Scoped lookups use a verified directory descriptor and `openat2` with beneath, no-symlink, and no-mount-crossing resolution. For file reads, the provider checks a pinned descriptor for a regular file with one link before opening it for data. Rename and replacement races cannot redirect that open through an unchecked path. The authorization point is the scoped lookup of the opened object. Successive list and read operations can observe different filesystem versions.

- `list({path, after, limit})` returns `{entries, next}` with up to 64 UTF-8 names in lexical order. Entries are pairs of name and `file` or `directory`. The empty path selects the root. Each call examines at most 4,096 directory entries.
- `read({path, offset, limit})` returns `{bytes, next}` with up to 8 KiB represented as byte integers. A null cursor means end of file.
- `readText({path, limit})` returns a whole UTF-8 file up to 16 KiB and fails if it exceeds the requested limit.

## Native application lifecycle

The source project maps named modules to files and capability requests to module names. Installation compiles these modules and resolves their content addresses before package review. Publishing exposes the selected immutable package and its program dependencies together in one transaction.

A `PPA1` block names a JavaScript entry point, graph budget, and remote capability requests. Its content address covers the full manifest and its Merkle edges retain the entry, requested programs, and their imports. A workspace resolves modules from its cache or explicitly selected, authenticated code peers. Existing peer discovery locates the selected identities. The application needs neither their addresses nor a deployment graph.

An installed package has a random stable installation ID, its own collection, and program-pinned local read and writer grants. The workspace peer identity authenticates remote calls. The user explicitly attaches each remote grant against an approved named request and the runtime presents it through the existing graph binding interface. The issuer controls the resource, holder, program, and revocation. Updating changes the package atomically, preserves the private collection, and carries forward grants only for identical requests. Replacing a binding or installing an update renews the local entry and writer grants. Removal revokes local grants and deletes the private collection and bindings. Content remains eligible for garbage collection when no other root retains it. Issuing peers retain control over their grants and state.

The terminal launcher invokes the entry locally through the same isolated graph worker. The `event` host call returns `{type: "line", id, text}` for the current line, capped at 4 KiB. The event ID can serve as the operation ID for a leaf update. The entry returns `{lines}` with up to 64 lines and 16 KiB of text. The launcher escapes terminal controls before displaying the text. The program has no direct terminal I/O. The reserved `state` binding calls the same entry as a local leaf without a terminal resource. It allows atomic writes through the usual revision and operation receipt rules. A native leaf bound to the workspace peer also runs directly. Other calls use peer graph transport and discovery. Both routes enforce the issuing grant against the pinned program.

## Storage and distribution

SQLite provides indexed content and reference lookups, durable WAL commits, and concurrent snapshots. The daemon uses synchronous=FULL and a database page quota. Each successful update increments the local reference revision even if its content hash stays the same. Reference changes and publication require complete Merkle graphs. Garbage collection traces current references, published roots, active job blocks, active subscription programs, and verified or partially downloaded resource histories. It removes unreachable content and associated cache entries in one transaction. Workers take bounded copies of the blocks they use, which can outlive collection of an older revision. [SQLite WAL](https://sqlite.org/wal.html)

Indexed references store entries under the composite key (reference, key). A graph invocation accesses its one collection by exact key or by ordered prefix range using an exclusive cursor. Reads see one SQLite snapshot across all of their effects. A write runs a bounded transaction, sees its own writes, and commits the entry changes, revision, and receipt together. A guest failure or cancellation before commit rolls back the changes. SQLite serializes writers at the database level. A pending graph read can hold its snapshot through remote effects for up to the bounded deadline. An ordinary indexed reference uses a placeholder block. A replicated indexed reference retains each committed state as an immutable manifest pointing to content-addressed entry blocks.

An immutable block's SHA-256 address covers its version bytes and contents. Public fetches serve blocks explicitly published by the local administrator. Publish dependencies individually when making a complete program available. An authorized caller can supply missing code over the existing authenticated connection. Supplied modules are cached in the submitting identity's scope. Only explicitly published code is shared across principals. Client-supplied packages are restricted to the declared import graph, regardless of what the remote peer requests.

Peers find content by hash through a local cache, explicitly configured sources, or bounded probes of discovered identities. Discovered LAN peers are probed before other peers. On a cache miss the authorized caller may supply the code first, followed by discovered sources. Each receiver verifies the hash and format of all returned blocks. In stable identity mode, publication serves the specified hash to authenticated peers. Unpublished blocks, scoped code caches and values in private references require their respective access paths.

## Replicated resources

An owner can share a snapshot or indexed reference under a stable random resource ID. Its immutable state has a content hash. Each signed revision has its own content hash and records the resource ID, state root, parent revisions, and author. Reference names are local aliases. A local numeric revision counts changes to that peer's visible head set and serves as the optimistic transaction guard. Compare peers using the signed revision IDs and head sets.

| Resource mode | Read consistency | Write semantics |
| --- | --- | --- |
| Immutable | Owner-authoritative, replica, or exact revision | One fixed initial revision |
| Single writer | Owner-authoritative, replica, or exact revision | Only the owner commits, through the existing expected-revision transaction |
| Multi-writer | Replica or exact revision | The owner and approved writers can commit locally, including while disconnected |

An invocation explicitly selects authoritative, replica, or a specific immutable revision. A replica read reports all locally accepted heads and selects the lowest revision ID in byte order as the state to evaluate. A revision read can select any verified, accepted historical revision. A writer encountering multiple heads must submit an explicit merge with the current local numeric revision. The merge program can use the sibling snapshots to construct its result. A successful merge records every current head as a parent. A change arriving later can create a new branch and require another merge. No update is discarded based on clock order. Resource views report the resource ID, mode, consistency, selected revision, and heads. JavaScript snapshot programs receive the view as a third argument. Indexed programs receive it through `pp2.storage.view`. Graph calls and durable job results return the view alongside the local revision and value.

The owner signs a versioned placement policy for stable peer identities. Each placement allows storage and synchronization, and can additionally allow local reads or local writes. Write placements require a multi-writer resource. A placement can pin a program hash. Read and write execution at a replica also requires a local, holder-bound capability within that placement's limits. Replica grants are bound to the workspace identity. A native leaf can execute in that workspace with its local binding, subject to the same grant and consistency checks. Bindings to other peers use their issuing peer's grant. A store-only placement participates in synchronization through the trusted daemon. Placement approval therefore includes trusting that host's operator with the stored plaintext.

Peers pull over the stable-identity transport. The signed policy and the serving peer's head IDs identify work to do. The receiver walks the existing block links and requests missing hashes in bounded passes. It checks content addresses, block format, revision signatures, parentage, and author authority before admitting a revision. Verified blocks and pending tips are durable garbage collection roots while an import is in progress. Once a tip and its dependencies are present, the peer commits the verified history, the selected state, and its local change event together. Synchronization can run between replicas while the owner is away and both leases remain current. Peers use existing discovery or pinned routes. Private blocks use resource-scoped synchronization. Public fetch and discovery expose only independently published bytes, and the peer rejects publication of unpublished resource blocks.

### Offline authority and revocation

The owner issues signed placement leases with a validity interval of up to 24 hours and sets the start two minutes before its clock at issuance. The owner renews a lease during synchronization when its remaining time falls below 12 hours. Each trusted daemon tests its own clock against that interval when executing or serving requests. Slow or fast clocks can change when peers reject the same lease. The replica can contact the owner to renew and resume from its retained history.

A signed revision authenticates the writer's claimed authoring time. A writer with the signing key and a copy of an expired lease can sign a fresh revision while claiming a time during that lease. A receiving peer checks the claim against the signed interval, placement, program pin, and accepted ancestry. If the placement is still active in its policy, it can accept that revision after the lease's end. The program hash is a claim by the writer's daemon. It proves which program was permitted and relies on that daemon to enforce which program executed. These properties assume protected keys, trusted daemons, and clocks within the deployment's expected skew. Timestamps have no role in resolving concurrent writes.

Revocation removes the placement in the owner's next signed policy. For a revoked writer, only changes already in the ancestry of the owner's accepted heads at revocation survive. Acknowledgment on an offline writer means the write is durable there, subject to the owner enforcing a later retirement cutoff. Peers that observe the policy exclude other changes from that placement and their descendants, and retain verified local records with their validity flags for audit. A replica that observes its own removal stops releasing state, signing changes, and serving blocks, and loses its local grants and affected subscriptions. It can receive policy information from the owner to learn of revocation or subsequent approval. Revocation cannot erase data already released to a process or another host. A disconnected replica can continue within its remaining lease until it sees the revocation.

Imported head changes use the existing local subscription queue and cursor. A synchronization batch can advance the visible state by several authored revisions and produce one local event. Replica entries execute with replica consistency. New subscription work waits during a temporary lease expiry, subject to the existing event retention window. Installed native applications keep their package and local binding across daemon restarts. Signing and lease state reside in the workspace alongside its peer database.

Collection manifests use the existing 256 KiB block size and a limit of 4,096 keys. A policy supports up to 32 active placements and 128 retired placements, and a resource has at most 128 heads. Host resources and native installation state use their local backing stores. A native app can bind a separate replicated resource for shared state.

### Snapshot retention

Single-writer resources can set a workspace-local snapshot limit with `pp2 peer replica retain HOME RESOURCE SNAPSHOTS`. The limit follows parent order from the head and applies when the visible history advances. Garbage collection releases unretained payloads that other references, publications, or pending transfers do not hold. It preserves signed revision blocks and parent edges. Exact reads of pruned revisions return an unavailable error even if a separate reference still holds the bytes. Increasing retention applies to future imports and writes. History reports the retained flag alongside revision validity. Acknowledged operation receipts remain available within the ordinary receipt window and authorization rules.

A follower first attempts full synchronization. A resource-scoped unavailable reply can trigger proof-only catch-up when the signed policy declares a single writer. The follower validates the owner, ancestry, and complete advertised head state before projecting the result. Imported ancestors retain their proofs only. A transfer that cannot obtain the full head fails without advancing that head locally. Placement denials end the transfer. Progress between passes is durable. Offline catch-up still requires an authorized source and a current placement lease.

Retention starts when configured, including for workspaces migrated from schema 6. Older binaries still speak the same wire protocol with upgraded peers that serve the requested full history. Upgrade followers before compacting their source so they can use proof-only catch-up. Back up the workspace before upgrading if binary rollback is needed. Single-writer snapshot pruning pauses if a restored or copied owner key produces multiple heads.

Signed ancestry continues to grow within the workspace's SQLite quota. Multi-writer resources still retain full revision history, including rejected records. Safe pruning there requires retaining every unresolved head and the ancestry needed to reconstruct and enforce signed retirement cutoffs when peers reconnect.

## TypeScript, JavaScript, and binary programs

A pp2 JavaScript program is an ECMAScript module with a default function. Snapshot programs take (state, input). Collection programs take (pp2, input), where pp2 provides the invocation's storage and authorized effects. A handler can return a JSON-compatible value or a promise of one. A read returns the value. An update returns an object with next and value fields. State and input are detached values. The wire boundary accepts text, booleans, null, safe integers, arrays, and records. Serialization checks depth, size, and numbers and rejects cycles and unsupported values. ECMAScript property access and toJSON behavior apply during serialization. Code can capture values in ordinary lexical closures within an evaluation. Across evaluations, recreate closures from the same module and explicit data. JavaScript structured cloning rejects callable objects, and V8 startup snapshots are engine initialization artifacts. [HTML structured serialization](https://html.spec.whatwg.org/multipage/structured-data.html), [V8 embedding guide](https://v8.dev/docs/embed)

The packaging command compiles TypeScript on the author's machine with strict ES2022 settings. It type-checks local source dependencies and links runtime imports to explicit hashes. TypeScript errors show source paths and line numbers. The program hash covers the emitted code and import manifest. Types are erased, so code still uses runtime checks when it accepts untrusted input. The TypeScript compiler runs only during packaging. [TypeScript compiler options](https://www.typescriptlang.org/docs/handbook/compiler-options.html)

A `PPJ1` module carries UTF-8 ECMAScript with a sorted list of SHA-256 import hashes. Use `SPECIFIER=HASH` to link a TypeScript import during packaging. A JavaScript module can write `pp2:HASH` directly and declare that hash as a positional pack argument. The loader resolves imports only against the verified manifest. Each worker installs a fresh context. The guest globals omit `Date`, `Math.random`, and shared-memory facilities. The locked QuickJS version supplies the ECMAScript semantics. Runtime exceptions identify emitted module locations by content hash.

V8 is a viable ECMAScript engine for larger workloads. Its standard embedding supports isolated heaps and separate contexts, and its in-process sandbox limits the impact of some engine memory faults. A V8 adoption would still require OS process isolation, controlled module loading, and explicit data and capability boundaries. QuickJS provides module hooks, an interrupt handler, and memory/stack limits, and builds from the locked source dependency without a JIT. These properties fit pp2's current isolated per-request worker. The graph comparison measures the whole invocation and reports aggregate worker time, including engine initialization, data conversion, and guest evaluation. [V8 sandbox](https://v8.dev/blog/sandbox), [V8 untrusted-code guidance](https://v8.dev/docs/untrusted-code-mitigations), [QuickJS embedding API](https://www.bellard.org/quickjs/quickjs.html)

Existing AEB1 programs still use the Rust interpreter and their original canonical encoding. A remote binary program sees slot zero as a read-only grant for its snapshot and obtains other portable inputs from its captures. JavaScript and binary IR use the same transport, grant checks, commit path, and process boundary.

## Isolation and limits

The worker receives verified code and arguments, plus either a granted snapshot or the named capabilities for a graph invocation. It starts with a cleared environment, closes inherited descriptors, and installs a Linux seccomp allowlist before reading the request. The filter allows pipe I/O on the designated descriptors and restricts memory mappings. File opens, socket operations, subprocess creation, and executable mappings are outside the allowlist. Resource limits bound address space and CPU. The peer also caps concurrent connections and frame sizes, and a parent watchdog stops expired workers. QuickJS limits its heap to 32 MiB and execution to two seconds excluding time waiting for the host on an effect. The host's graph deadline includes those waits. Binary IR keeps its fuel and charged allocation budgets. JavaScript reports a heap sample at completion and worker elapsed time. [seccompiler](https://docs.rs/seccompiler/latest/seccompiler/)

The daemon is the trusted host for credentials, the database, and grant policy. Worker pipes carry a typed and bounded request/reply protocol. The host validates every effect, holds all sockets and transaction handles, and gives the worker values and status only. It checks the worker result before publishing it to the caller or committing state. A read grant can permit arbitrary programs to observe its entire snapshot. Restrict a grant to an audited program hash when the caller should see only the results that program exposes.

The peer transport and worker envelope use `PPN1`, a 32-bit big-endian length, and a Postcard payload. Reactions, synchronization, and resource-aware results use additional message variants. Existing evaluation, fetch, delegation, and durable job messages preserve their wire encodings. Immutable `AEB1` and `PPJ1` blocks and `AEV1` portable values retain independent formats. Databases migrate transactionally. Schema version 4 added subscriptions and reaction job metadata. Version 5 added host resources, native installations, and bindings. Version 6 added replication policies, histories, and progress. Version 7 adds snapshot retention and durable proof-only catch-up. Existing references retain their revisions. Blocks and portable values are limited to 256 KiB each. A code graph can contain up to 32 modules and 512 KiB. Remote code caching has a 16 MiB cap per holder. A discovered content resolution makes at most 64 fetch attempts within the existing operation deadline. A missing result means that the search found no verified copy in its discovery scope.

## Snapshot application measurements

The reproducible comparison in scripts/validate-peers.py uses the same synthetic document queries for both implementations. It measures warm indexed reads over loopback with a fresh mutual TLS connection for each query. The conventional implementation uses an application-specific HTTPS endpoint, certificate policy, and SQLite FTS5 query. The pp2 implementation supplies application-specific indexing and query modules, with TLS, framing, grant validation, and execution handled by the daemon. Wire counts include application framing and exclude TLS records. Timings include network connections and exclude client process startup.

The 40-query run used 64 documents with 121,648 bytes of body text. Both systems returned identical results.

| Implementation | Median latency | Request | Response |
| --- | ---: | ---: | ---: |
| pp2, warm | 11.00 ms | 129 B | 393 B |
| HTTPS with SQLite FTS5 | 6.65 ms | 57 B | 441 B |

The cold pp2 request against an empty library included module negotiation and took 19 ms, with 1,916 B sent and 108 B received. Each call starts a new worker and decodes a full reference snapshot.

The conventional search service owns its HTTP request and response schema, its certificate-to-route check, and its SQL query. The pp2 modules own the index and query, while both applications use one server implementation for authentication, versioned writes, and retry receipts. The comparison covers search only. Application complexity and reliability across identical feature sets, WAN latency, and larger libraries require further measurements.

The separate Linux network namespace run exercised peer-sourced application updates, queued edits, cached reads, and restart recovery. ## Three-peer graph measurements

The release graph benchmark uses stable identities on three Linux network namespaces connected by virtual Ethernet on one host. West and east each hold 20,032 entries in 1,314,816-byte pp2 databases. Each warehouse matches 32 rows and scans two pages. Direct and delegated invocations return the same stock totals as the conventional implementation.

The distributed comparison runs an application-specific stock service and uses SQLite and framed JSON. Both services authenticate the caller and destination and open a fresh TLS 1.3 connection per edge. The conventional service enforces fixed certificate pins and routes. The pp2 application supplies grants for program and collection access and runs each guest in a fresh isolated worker. The mTLS baseline covers the same stock query and caller restrictions. The delegated pp2 graph also exercises grant attenuation and has a different call topology. Timing starts within the client and includes connection setup. Byte counts cover application frames across all edges. Both implementations used the host's page cache.

JSON events on stderr report the peer, program, caller, durable job ID where applicable, durations, memory sample, and failure class. ## Operational validation

The seeded Notes run uses three separately initialized identities and workspaces and three independently switched veth links. Each round gives two writers different histories, forces an authenticated network request to fail during the partition, kills both writer daemons after acknowledgments, and then reconnects them. The observer checks the complete state against a model of both branch snapshots. Every conflicting text remains visible until the script issues an explicit resolution. The run also checks catch-up with an unavailable owner, revocation of application and saved-job access, and native package removal.

The 10-round run with seed 761 and 25 operations per writer per round acknowledged 591 updates and merges in 63.54 seconds, including partitions and recovery. The two-head recovery took 3.09–3.38 seconds per round. The main database files ended between 2.46 and 2.58 MB per peer, with WAL and temporary files outside those totals. Four more rounds with seed 793 acknowledged 231 updates and merges. A separate 40-commit single-writer check compacted to four retained snapshots, killed the source after the first 32-block sync pass, collected unreferenced target blocks, and resumed with 13 blocks. The follower verified 41 signed revisions and read the current state. The catch-up and restart took about 0.72 seconds, and a subsequent sync transferred zero blocks.

The configured limits include 16 inbound connections per daemon, four durable workers, 64 active durable jobs per workspace with up to 32 per holder, and up to four leaf reads in a batch. A graph budget permits at most 16 child calls, depth four, and eight seconds. A synchronization pass transfers up to 32 blocks. The database main file has a 65,536-page cap, typically 256 MiB with 4 KiB pages. SQLite WAL, block staging, and retained history contribute to storage requirements. Disk exhaustion rejects the transaction, and a retry can commit the operation after space is available. The Notes guest caps its collection at 32 titles.

A separate graph load check measured 122 and 151 successful queries per second at 4 and 16 concurrent CLI clients. All 88 queries succeeded at those levels. At 24 clients, 16 of 72 queries reported `peer-unavailable`, and a subsequent query succeeded. Throughput includes client process startup. These short runs characterize one host and this workload. Sustained throughput and latency under WAN conditions remain to be measured.

The real-machine acceptance run requires a separately developed application and three independently administered machines. Use the public installation, update, binding, and removal interfaces with separately generated identities and pinned program hashes. Keep a matched conventional deployment with equivalent data and access controls. Record workload size, acknowledged operations, accepted heads, resource usage, and client latency through disconnects, restarts, revocation, and recovery. That trial is pending.

## Current scope

- Discovery uses local multicast and an optional bounded rendezvous directory. Across NATs, operators can enable relaying or advertise directly reachable addresses.
- Transactions are local to one collection. The graph API exposes the outcome and revision of each child operation. Multi-reference transactions and bounded multi-writer history remain open.
- Interactive runtime debugging, TypeScript source maps for remote errors, and portable JavaScript closure state remain open.
