# Runtime design

## Evaluation and authority

A peer accepts one operation per mutually authenticated TLS 1.3 connection. It looks up the capability by both its random ID and the caller's authenticated identity. The peer controls the reference the capability addresses. A grant allows snapshot reads or snapshot reads and atomic updates. Indexed references grant reads or reads and transactional row updates. A grant can restrict either kind of reference to one immutable program hash. A grant holder may delegate an equal or narrower grant to a different identity, with a maximum depth of eight. Revoking a grant removes its descendants and their receipts in the same transaction.

A snapshot read runs against one immutable state block. The peer rechecks authorization before releasing a result. A snapshot update uses an expected revision and returns exactly {next, value}. The peer checks the revision and grants inside the committing transaction, then saves the next content block, the reference advance, and a receipt together. Concurrent successful updates to a reference have a total order. Reads see the revision they started with. Storage is single-writer per reference revision, with one authoritative storage peer.

Use the same grant, program, input, expected revision, and operation ID when retrying an ambiguous update. A recent match replays the receipt. Reusing an ID with different arguments while its receipt is retained produces an error. Receipts are retained for 1,024 revisions while the grant remains live. When the revision has advanced past that window, a conflict can establish that the retry did not apply now. The client must reconcile older outcomes through application state. The original `peer delegate` creates a distinct grant on each success. The graph attenuation operation described below replays the same live grant for an identical request.

The caller chooses the entry peer. The client reports elapsed time and application bytes in both directions, including code negotiation. Rust callers can use `Cancellation` to close a synchronous evaluation. Its worker stops when the request connection closes or the daemon exits. Cancellation can race a commit, so recovery uses the same update receipt mechanism.

## Peer identity and discovery

In stable identity mode, a peer ID is a domain-separated SHA-256 hash of an Ed25519 public key. Peers sign role-specific TLS 1.3 exporters to prove possession of the corresponding private key on the current connection. The client verifies the expected destination ID before presenting its own proof or sending any grant, program or input. The server checks its local identity policy before accepting a pp2 request. Independently administered nodes can use their own transport certificates, including self-signed certificates. The certificate authenticates the TLS handshake key and the exporter proof establishes the pp2 identity. Certificate mode continues to use CA validation, TLS names and certificate fingerprints.

Address changes and transport certificate replacement retain the same identity when the operator keeps the identity key. Replace a lost or compromised identity key by provisioning a new ID and reissuing grants and bindings for that ID. Jobs and subscriptions remain bound to the identity that submitted or installed them. Resume work under a replacement identity by explicitly resubmitting or reinstalling it under new grants. To deny a compromised identity at a node, add its ID to `revoked` in that node's discovery configuration and restart the daemon. It then rejects inbound and outbound sessions for that identity and queued jobs submitted by it. Each resource owner can revoke the affected grants to remove their delegated descendants. Revocation policy is local to each operator.

Listening peers sign short-lived location leases. IPv4 LAN advertisements use multicast group `239.255.73.42:47342` with a one-hop limit. The listener periodically refreshes its selected interface, including after an address change. A received lease supplies a LAN route when its signed LAN address matches the datagram source. Every route still requires the TLS identity proof. A lease expires eight seconds after issuance and the receiver accepts issuance at most two seconds ahead of its clock. The newest valid lease supersedes older leases. Conflicting locations with the same issuance time quarantine the identity's discovery routes until a newer valid lease arrives or the leases expire. Explicitly pinned routes can still authenticate the identity during a discovery conflict. Operators run one active endpoint advertiser per identity and keep clocks synchronized.

A node can publish the same leases to a configured rendezvous service. It can also offer up to two outbound sockets for the relay to pair with incoming connection attempts for its ID. A fresh, signed challenge proves possession of the receiving identity before a socket can be offered. A paired socket carries the same end-to-end TLS handshake and operation as a direct connection. The service can observe connection metadata, withhold leases or drop traffic. Destination authorization, the operation state and the encrypted payload stay with the peers. Each node tries live LAN routes, configured pins and signed direct addresses before relaying. Once a route is authenticated and a request sent, the transport leaves ambiguous operations to the existing receipt or job retry mechanism.

The directory retains up to 64 identities and each lease can advertise four direct addresses plus its LAN route. Rendezvous caps simultaneous control requests at 32 and, when enabled, relayed sessions at 32. Each tunnel has a 12-second lifetime and an 8 MiB allowance per direction. Discovery work fits inside the caller's deadline and uses bounded route attempts and frames. A synchronous invocation can report `peer-unavailable` when it cannot establish an authenticated route or `timeout` when its deadline runs out. Durable effects retry temporary unavailability until their deadline. Locally available work and configured direct paths can run while rendezvous is offline. [TLS 1.3 exporters](https://www.rfc-editor.org/rfc/rfc8446#section-7.5)

## Guest effects and placement

A graph starts at an explicitly selected peer against one indexed reference and one program. Its input includes a deadline, a call count, a maximum depth, and named capabilities. The executing peer resolves named local bindings against the authenticated caller identity, entry grant, and entry program. An authenticated peer can also attach recipient-bound grants. Attachments contain an issuer identity, opaque grant ID, pinned program, and access. The host resolves that identity to a route and authenticates the destination before sending a grant.

The worker sees opaque JavaScript objects with invocation-local identity. It can pass an explicit subset to `pp2.evaluate`. JSON values convey no authority. For each selected capability, the current executor asks the issuing peer to narrow it to the child identity, program, permitted access, graph limits, and expiry. The child holds those capabilities and authenticates to the next destination as itself. The destination checks the authenticated holder, the presenting peer associated with the attachment, the program and operation, the active grant lineage, and all grant ceilings. Issuers deny authority expansion and remove descendant grants on revocation. The guest sees only the resulting invocation-local objects.

Each call consumes one graph call plus the descendant allowance assigned to it. Every executor applies the remaining depth and budget to its own outgoing effects. The hard ceilings are 16 remote calls, four remote levels, 16 bindings per invocation, and eight seconds per attempt. A branch may shorten the inherited deadline. Each worker can submit up to 128 effects, and failed calls consume their reservations. Metrics aggregate remote attempts, frames, and results reported by participating peers.

Synchronous calls remain tied to their immediate connection. Closing the entry connection stops its worker and closes its outstanding child connection, which propagates cancellation down the active branch. Guest promises enqueue effects in order. Returning with unsettled effects fails the invocation.

An update is a leaf. It names an expected collection revision and operation ID. Commits and receipts belong to the destination, and a failure later in the graph leaves an earlier committed update in place. Independent peers can observe different revisions. The update receipt rules apply to synchronous retry.

## Durable computations

A durable job uses the graph evaluator and the same worker isolation. Its identity is the submitting peer identity and a client-chosen job ID at the selected peer. Acceptance commits the immutable program and input hashes, the verified code and input blocks, the resolved capabilities, the graph budget, and the absolute expiration. Binary database timestamps use Unix milliseconds. Peers need reasonably synchronized clocks for deadlines. An identical submission retrieves the stored status. Changing an argument under an existing identity fails.

The peer owns the job after acceptance. It runs up to four durable attempts concurrently, with at most 32 active jobs per submitter and 64 per peer. A new job may live up to five minutes. The attempt deadline and worker limits apply each time it runs. One daemon serves the database at a time. After a process restart it requeues interrupted attempts from SQLite. Garbage collection retains the verified input and program graph while a job is active. Terminal job IDs, program and input hashes, and results are retained in the database and share its page quota.

A durable remote effect first records its intent and a stable child ID, then submits a durable child directly to its destination. Pending children and temporary transport failures cause the parent to yield its worker and retry. The parent journals terminal child outcomes. Re-evaluation can reuse those outcomes or retrieve them from the child if acknowledgment was lost. Changing or skipping a previously recorded remote effect fails recovery. Local reads are snapshot-consistent within each attempt and can observe a new revision on replay.

A durable local update commits collection changes, revision, retry receipt, and job completion in one SQLite transaction. A crash before that transaction commits rolls it back. Workers and messages can repeat, and child effects use durable identities to recover their committed outcomes. Transactions cover an individual peer and collection.

The submitting identity can query or cancel its jobs on a new connection. A committed cancellation stops local execution and prevents local completion. If completion won the race, cancellation returns the completed state. Expiration prevents new work and commits under that job's execution deadline. Children already accepted at other peers can finish within their own bounds, and committed effects remain in place. An entry grant revoked before completion denies further work under that grant. Terminal outcomes belong to the submitting identity and remain retrievable after grant revocation.

## Persistent applications

A local administrator installs a named application for the daemon's authenticated identity. The database retains each subscription's immutable JavaScript program, local watch and entry grants, named remote grants, graph budget, expiration, and delivery cursor. Installation validates the full handler module graph and pins it for garbage collection while the subscription is active. The watch and entry grants must each be read-only, bound to the daemon's identity, and pinned to the handler. The watch grant identifies one reference. The handler reads from the indexed collection selected by the entry grant, which defaults to the watch grant. Remote capabilities come from the installation and remain subject to the issuer's identity, program, access, delegation, and expiry checks.

Each reference creation and successful revision advance commits an event with a stable random ID in the same transaction as its state changes. An operation receipt replay returns the original result without a second revision or event. A subscription starts at the current revision on installation. Events carry the reference name and revision. They carry no snapshot or row values. Handler reads see the collection snapshot for the current attempt. An application that needs the values from a specific revision can store them under an immutable revision key in the same transaction as the resource update, as the inventory example does.

The daemon enqueues at most one delivery per subscription at a time, in revision order. Acceptance durably associates the event and subscription with a deterministic job ID and journals remote effects through the existing durable job mechanism. On completion, the daemon retires the revision and stores its terminal outcome atomically. Temporary transport or storage failures retry within the job's deadline. Handler failures, authorization failures, and expired deliveries retire the revision and let the next event proceed. Worker attempts may repeat, and a child may commit before a later effect fails. Use stable operation IDs and idempotent application updates where retries matter.

Each application can install up to 16 subscriptions and a peer can have up to 128 active subscriptions. Deliveries share the four durable workers and the existing active job limits. A full queue leaves events on the log, and a full destination queue returns a retryable busy response for reaction jobs. Each delivery lives for up to five minutes or until its subscription expires, whichever comes first. The event log keeps up to 4,096 events per peer. The serving daemon also prunes events older than 24 hours. A cursor that falls behind reports missing revisions and resumes at the next retained revision. Once enqueued, a delivery retains its event input independently of the log. Each subscription keeps its latest terminal outcome. Remote reaction results remain available until five minutes after their deadline so a retrying parent can recover them.

Reactions run in the same bounded worker and graph as explicit durable jobs. The host propagates reaction origin to descendants. A destination must issue a pinned reaction-writer grant for a reaction to update its collection. Ordinary updates require ordinary grants. Reaction writes create events, and subscription cursors skip those events at every peer. This bounds execution to one generation of subscriptions per ordinary state transition while allowing the reaction's explicitly budgeted graph to use multiple peers.

The watched resource owner or entry resource owner can revoke the relevant grant, which cancels local deliveries and disables the subscription. The installer can also revoke a subscription directly. Removing an installation revokes its local subscriptions and cancels their pending and running jobs in one transaction. Before dispatching a child, the daemon records its absolute deadline. The application reports `removing` until those deadlines pass, and `removed` afterward. A child accepted by another owner may finish before its deadline or be cut off by that owner's revocation. Committed updates persist. Installation records and names are retained after removal. Resuming an installation requires the original serving identity.

## Storage and distribution

SQLite provides indexed content and reference lookups, durable WAL commits, and concurrent snapshots. The daemon uses synchronous=FULL and a database page quota. Each successful update increments the reference revision even if its content hash stays the same. Reference changes and publication require complete Merkle graphs. Garbage collection traces current references, published roots, active job blocks, and active subscription programs, then removes unreachable content and associated cache entries in one transaction. Workers take bounded copies of the blocks they use, which can outlive collection of an older revision. [SQLite WAL](https://sqlite.org/wal.html)

Indexed references store entries under the composite key (reference, key). A graph invocation accesses its one collection by exact key or by ordered prefix range using an exclusive cursor. Reads see one SQLite snapshot across all of their effects. A write runs a bounded transaction, sees its own writes, and commits the entry changes, revision, and receipt together. A guest failure or cancellation before commit rolls back the changes. SQLite serializes writers at the database level. A pending graph read can hold its snapshot through remote effects for up to the bounded deadline. Collection revisions identify committed contents. The placeholder block on an indexed reference carries no entry data and is outside the collection API.

An immutable block's SHA-256 address covers its version bytes and contents. Public fetches serve blocks explicitly published by the local administrator. Publish dependencies individually when making a complete program available. An authorized caller can supply missing code over the existing authenticated connection. Supplied modules are cached in the submitting identity's scope. Only explicitly published code is shared across principals. Client-supplied packages are restricted to the declared import graph, regardless of what the remote peer requests.

Peers find content by hash through a local cache, explicitly configured sources, or bounded probes of discovered identities. Discovered LAN peers are probed before other peers. On a cache miss the authorized caller may supply the code first, followed by discovered sources. Each receiver verifies the hash and format of all returned blocks, and a local operator may explicitly republish verified copies. In stable identity mode, publication serves the specified hash to authenticated peers. Unpublished blocks, scoped code caches and values in private references require their existing access paths. Mutable references belong to their authoritative peers, and snapshot contents retain their immutable addresses.

## TypeScript, JavaScript, and binary programs

A pp2 JavaScript program is an ECMAScript module with a default function. Snapshot programs take (state, input). Collection programs take (pp2, input), where pp2 provides the invocation's storage and authorized effects. A handler can return a JSON-compatible value or a promise of one. A read returns the value. An update returns an object with next and value fields. State and input are detached values. The wire boundary accepts text, booleans, null, safe integers, arrays, and records. Serialization checks depth, size, and numbers and rejects cycles and unsupported values. ECMAScript property access and toJSON behavior apply during serialization. Code can capture values in ordinary lexical closures within an evaluation. Across evaluations, recreate closures from the same module and explicit data. JavaScript structured cloning rejects callable objects, and V8 startup snapshots are engine initialization artifacts. [HTML structured serialization](https://html.spec.whatwg.org/multipage/structured-data.html), [V8 embedding guide](https://v8.dev/docs/embed)

The packaging command compiles TypeScript on the author's machine with strict ES2022 settings. It type-checks local source dependencies and links runtime imports to explicit hashes. TypeScript errors show source paths and line numbers. The program hash covers the emitted code and import manifest. Types are erased, so code still uses runtime checks when it accepts untrusted input. The TypeScript compiler runs only during packaging. [TypeScript compiler options](https://www.typescriptlang.org/docs/handbook/compiler-options.html)

A `PPJ1` module carries UTF-8 ECMAScript with a sorted list of SHA-256 import hashes. Use `SPECIFIER=HASH` to link a TypeScript import during packaging. A JavaScript module can write `pp2:HASH` directly and declare that hash as a positional pack argument. The loader resolves imports only against the verified manifest. Each worker installs a fresh context. The guest globals omit `Date`, `Math.random`, and shared-memory facilities. The locked QuickJS version supplies the ECMAScript semantics. Runtime exceptions identify emitted module locations by content hash.

V8 is a viable ECMAScript engine for larger workloads. Its standard embedding supports isolated heaps and separate contexts, and its in-process sandbox limits the impact of some engine memory faults. A V8 adoption would still require OS process isolation, controlled module loading, and explicit data and capability boundaries. QuickJS provides module hooks, an interrupt handler, and memory/stack limits, and builds from the locked source dependency without a JIT. These properties fit pp2's current isolated per-request worker. The graph comparison measures the whole invocation and reports aggregate worker time, including engine initialization, data conversion, and guest evaluation. [V8 sandbox](https://v8.dev/blog/sandbox), [V8 untrusted-code guidance](https://v8.dev/docs/untrusted-code-mitigations), [QuickJS embedding API](https://www.bellard.org/quickjs/quickjs.html)

Existing AEB1 programs still use the Rust interpreter and their original canonical encoding. A remote binary program sees slot zero as a read-only grant for its snapshot and obtains other portable inputs from its captures. JavaScript and binary IR use the same transport, grant checks, commit path, and process boundary.

## Isolation and limits

The worker receives verified code and arguments, plus either a granted snapshot or the named capabilities for a graph invocation. It starts with a cleared environment, closes inherited descriptors, and installs a Linux seccomp allowlist before reading the request. The filter allows pipe I/O on the designated descriptors and restricts memory mappings. File opens, socket operations, subprocess creation, and executable mappings are outside the allowlist. Resource limits bound address space and CPU. The peer also caps concurrent connections and frame sizes, and a parent watchdog stops expired workers. QuickJS limits its heap to 32 MiB and execution to two seconds excluding time waiting for the host on an effect. The host's graph deadline includes those waits. Binary IR keeps its fuel and charged allocation budgets. JavaScript reports a heap sample at completion and worker elapsed time. [seccompiler](https://docs.rs/seccompiler/latest/seccompiler/)

The daemon is the trusted host for credentials, the database, and grant policy. Worker pipes carry a typed and bounded request/reply protocol. The host validates every effect, holds all sockets and transaction handles, and gives the worker values and status only. It checks the worker result before publishing it to the caller or committing state. A read grant can permit arbitrary programs to observe its entire snapshot. Restrict a grant to an audited program hash when the caller should see only the results that program exposes.

The peer transport and worker envelope use `PPN1`, a 32-bit big-endian length, and a Postcard payload. Reaction submissions use a new request variant. Existing evaluation, fetch, delegation, and durable job messages preserve their wire encodings. Immutable `AEB1` and `PPJ1` blocks and `AEV1` portable values retain independent formats. Databases migrate transactionally to schema version 4, which adds applications, subscriptions, events, and reaction job metadata. Existing references retain their revisions and start recording events on the next commit. Blocks and portable values are limited to 256 KiB each. A code graph can contain up to 32 modules and 512 KiB. Remote code caching has a 16 MiB cap per holder. A discovered content resolution makes at most 64 fetch attempts within the existing operation deadline. A missing result means that the search found no verified copy in its discovery scope.

## Snapshot application measurements

The reproducible comparison in scripts/validate-peers.py uses the same synthetic document queries for both implementations. It measures warm indexed reads over loopback with a fresh mutual TLS connection for each query. The conventional implementation uses an application-specific HTTPS endpoint, certificate policy, and SQLite FTS5 query. The pp2 implementation supplies application-specific indexing and query modules, with TLS, framing, grant validation, and execution handled by the daemon. Wire counts include application framing and exclude TLS records. Timings include network connections and exclude client process startup.

The 40-query run used 64 documents with 121,648 bytes of body text. Both systems returned identical results.

| Implementation | Median latency | Request | Response |
| --- | ---: | ---: | ---: |
| pp2, warm | 10.00 ms | 129 B | 393 B |
| HTTPS with SQLite FTS5 | 6.10 ms | 57 B | 441 B |

The cold pp2 request against an empty library included module negotiation and took 25 ms, with 1,916 B sent and 108 B received. In the warm run, pp2 returned a smaller reply and spent more time per call. Each call starts a new worker and decodes a full reference snapshot. The measurements cover the whole evaluation path and leave those costs unquantified individually.

The conventional search service owns its HTTP request and response schema, its certificate-to-route check, and its SQL query. The pp2 modules own the index and query, while both applications use one server implementation for authentication, versioned writes, and retry receipts. The comparison covers search only. Application complexity and reliability across identical feature sets, WAN latency, and larger libraries require further measurements.

The separate Linux network namespace run exercised peer-sourced application updates, queued edits, cached reads, and restart recovery. It also ran two competing reservations against one available unit and replayed the winning update. The clients and storage peer used separate network stacks on the same host.

## Three-peer graph measurements

The measurements below are from the previous callback transport. `scripts/benchmark-graph.py --isolated-networks --samples 40` runs independent office, west, and east peer processes in Linux network namespaces connected by virtual Ethernet on one host. West and east each hold 20,032 entries in databases of 1,150,976 bytes. Each warehouse matches 32 rows and scans two pages locally. Both direct and delegated pp2 calls return the same stock totals as the conventional implementation.

The conventional in-process baseline queries the three SQLite databases directly using indexed SQL. The conventional distributed baseline runs the same SQL in dedicated stock services and uses a small framed JSON protocol. It authenticates the expected certificate at each peer and uses a fresh TLS 1.3 connection for each of the three edges, as pp2 does. Both network timings include connection setup and exclude the launch of the client executable. Framing byte counts include all application traffic across the three edges and exclude TCP and TLS overhead.

| Implementation | Median | p95 | Application bytes |
| --- | ---: | ---: | ---: |
| SQLite in process | 1.99 ms | 2.32 ms | — |
| Conventional mTLS and SQLite | 15.14 ms | 17.14 ms | 206 B |
| pp2 with cached programs | 25.04 ms | 26.26 ms | 544 B |

On this run the conventional service added 13.15 ms to the median in-process lookup. That difference estimates distribution overhead for this fresh-connection topology and includes TLS, protocol handling, and service scheduling. Warm pp2 added 9.90 ms relative to that service. Within pp2, the three workers accounted for a median aggregate 8.34 ms in process startup and IPC around execution and 4.69 ms actively initializing the runtime, converting data, and evaluating JavaScript. The indexed storage effects took 0.48 ms in aggregate. These summed worker measurements include time at different peers and cannot be added to the end-to-end median. The implementations also differ in TLS and SQLite drivers.

The first pp2 invocation took 66.05 ms and transferred 2,029 application bytes while the warehouses requested code. The delegated invocation then took 25.75 ms with code cached. The cold observation is one invocation with empty code caches. The working set may already be in the OS page cache. The results identify worker creation and cold code negotiation as runtime overhead. They give no WAN or throughput estimate.

## Current scope

- Discovery uses local multicast and an optional bounded rendezvous directory. Across NATs, operators can enable relaying or advertise directly reachable addresses.
- Transactions are local to one collection. The graph API exposes the outcome and revision of each child operation. Multi-reference transactions and storage replication are open.
- Runtime debugging, TypeScript source maps for remote errors, and portable JavaScript closure state remain open.
